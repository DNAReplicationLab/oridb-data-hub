# OriDB data hub

A UCSC track hub serving genome-wide DNA replication datasets for OriDB.

This repository holds **presentation**: bigWig tracks, their display configuration, and a
record of where each dataset came from. It does not process data. Each dataset is produced
by its own pipeline and deposited here as a self-contained directory.

The first dataset, `muller2014`, comes from
[Muller-replication-timing](https://github.com/DNAReplicationLab/Muller-replication-timing).

## Layout

```
hub.txt                       hub-level metadata
genomes.txt                   which assemblies are served
sacCer3.chrom.sizes           one per assembly, used by the validator
GCF_000002945.1.chrom.sizes
sacCer3/
  trackDb.txt                 nothing but `include` lines, one per dataset
  sacCer3.2bit                the sequence, for viewers that fetch it themselves
  sacCer3.refNameAliases.txt  chrI = I = BK006935.2 = NC_001133.9, and so on
  muller2014/
    trackDb.txt               that dataset's track configuration
    dataset.json              accessions, strains, per-sample statistics, checksums
    *.bw                      the tracks themselves
    *.peaks.bed, *.peaks.bb   call sets derived from those tracks, with their .as
  oridb_v3/                   OriDB's own records, rendered as bigBed
GCF_000002945.1/              S. pombe tracks, drawn on UCSC's GenArk copy of ASM294v2
bin/
  make_trackhub.py            generate or refresh one dataset's stanza
  validate_hub.py             check the hub before serving it
docs/adding-a-dataset.md
docs/trep_peak_calls.md       how the muller2014 origin calls were made
```

One directory per dataset, with its own `trackDb.txt`, is what makes the hub additive: a
new dataset never requires editing an existing one's configuration, and a dataset can be
regenerated by its own pipeline without anybody merging track definitions by hand.

### The sequence files, and who reads them

UCSC fetches sequence from its own servers for `sacCer3`, so the `.2bit` beside the
tracks is not for UCSC: it is for a browser embedded in a web page, which has to read the
reference itself. *S. pombe* has no UCSC database, but UCSC's GenArk collection hosts the assembly as
`GCF_000002945.1`; the hub names that accession and adds tracks to it, so readers get
UCSC's gene annotation alongside. The `.2bit` kept in that directory is for the embedded
viewer only.

`sacCer3.2bit` is UCSC's own file, verified against the md5 UCSC publishes
(`880201a7d1ec95c0185b0b4783c80411`). `GCF_000002945.1.2bit` is built from the RefSeq copy of ASM294v2
(`GCF_000002945.1`, GenBank `GCA_000002945.2`) with the sequences renamed from accessions
to `I`, `II`, `III` and `MT`, which is also the `assembly` naming in UCSC's own chromAlias
for it. The later assembly `ASM294v3`
(`GCA_000002945.3`, which is what UCSC serves) carries the **same three nuclear chromosome
sequences, under the same accessions and at the same lengths**; only the mitochondrial
sequence differs, by two bases. Nuclear coordinates are therefore interchangeable between
the two, which is why OriDB's pombe records can be linked to either.

The `refNameAliases` files are for viewers that must reconcile namings: each line is the
name this hub uses, followed by the names other sources use for the same sequence.

### OriDB's own records

`<genome>/oridb_v3/` is not a published dataset. It is the OriDB release itself rendered
as bigBed — origin intervals coloured by evidence tier, origin elements, and the fragments
that failed an ARS assay — so that a reader looking at somebody's profile can see what the
database says about the same window. The files are generated by
`bin/build_oridb_tracks.py` **in the oridb-v3 repository**, not by a pipeline here, and
their `dataset.json` records the release and the checksum of each file. They are rebuilt
when the database is, which is the one dataset directory here that is expected to change
with every release.

## Using it

Paste the URL of `hub.txt` into
[UCSC's Track Hubs page](https://genome.ucsc.edu/cgi-bin/hgHubConnect), or append
`hubUrl=<url to hub.txt>` to a Genome Browser link. The files must be served over HTTPS
from a host that honours byte-range requests.

**If you will also embed JBrowse 2 or igv.js on oridb.org**, the host additionally needs to
send `Access-Control-Allow-Origin` — those render in the reader's browser rather than on
the browser's server, so they are subject to CORS. UCSC and Ensembl fetch server-side and
do not care.

## How the sync-seq time course is displayed

The seven sync-seq timepoints are a `multiWig` container with `aggregate
transparentOverlay`, so all seven are superimposed on one track rather than stacked as
seven rows. The whole point of a replication time course is how the profiles rise against
each other at the same locus, and a reader can only see that when they share an axis.

Colours follow Müller *et al.* 2014 Figure 3D, so a timepoint is the same colour in the
browser as in the paper:

| timepoint | colour | RGB |
|---|---|---|
| 25 min | light blue | 166,206,227 |
| 30 min | red | 227,26,28 |
| 35 min | blue | 31,120,180 |
| 40 min | gold | 255,193,7 |
| 45 min | green | 51,160,44 |
| 50 min | purple | 106,61,154 |
| 90 min | grey | 150,150,150 |

`viewLimits` is `1:2` for every copy-number track, because that scale means something:
1 is unreplicated and 2 is fully replicated. Smoothed profiles overshoot it slightly and
are clipped, which is deliberate — `bin/validate_hub.py` reports how much is clipped and
only fails when a track's *mean* falls outside its limits, which would mean the limits
themselves are wrong.

## Validating before serving

```bash
python3 bin/validate_hub.py --hub-root . --chrom-sizes sacCer3.chrom.sizes
```

It follows the `include` chain, checks every `bigDataUrl` resolves **the way UCSC resolves
it** — relative to the trackDb named in `genomes.txt`, not relative to the included file —
checks every subtrack has a parent, and checks every track's sequence names and lengths
match the assembly. A hub that is
wrong in any of these ways fails in the browser with a message naming a line in a file the
reader has never seen, so it is worth catching here.

Note for anyone extending the tooling: do not use `pyBigWig`'s `header()` to read a track's
value range. In 0.3.30 it casts `minVal`/`maxVal` to int, so a profile spanning 0.93–2.28
is reported as 0–2. The file is correct; the accessor is lossy. `bigwig_summary()` in
`bin/validate_hub.py` reads the total-summary block directly.
